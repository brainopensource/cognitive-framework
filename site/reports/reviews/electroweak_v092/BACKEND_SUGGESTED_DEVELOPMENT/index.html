    Executive summary

    1. AETHER is an event-sourced agentic computation substrate.
    2. Vanguard is its backend runtime and composition framework.
    3. The framework is not fundamentally a chatbot framework.
    4. It is not fundamentally a coding-only harness.
    5. It is not fundamentally a workflow-DAG product.
    6. It represents execution as typed causal operations.
    7. An agent is a projection over identity, policy, lineage and events.
    8. An in-memory agent object is not required for continuation.
    9. A process can terminate without destroying semantic state.
    10. Another process can reconstruct the run from durable facts.
    11. Large data is stored as content-addressed artifacts.
    12. Events contain causal facts and references to larger artifacts.
    13. Projections provide queryable views of those facts.
    14. Caches and indexes never become a second source of truth.
    15. The kernel mediates privileged effects.
    16. Agency runs model-driven turns.
    17. Runtime composes and persists executions.
    18. Adapters connect models and environments.
    19. Packs define domain behavior outside the kernel.
    20. Applications expose useful vertical products.
    21. Coding, research and tutoring are compositions, not new runtimes.
    22. The architecture therefore generalizes by composition.
    23. Generalization must not become uncontrolled abstraction.
    24. The trusted core is intentionally small.
    25. Domain policy stays above the trusted core.
    26. Infrastructure implementations stay behind ports.
    27. Runtime authority stays in one place.
    28. Evidence authority stays exterior to the agent.
    29. Completion is admitted by applicable evidence.
    30. This is the strongest architectural asset of the project.

    14. Topology mechanisms exist but require qualification evidence.
    15. Adaptive controller mechanisms exist but remain conservatively disabled.

    17. Product integration is less complete than primitive coverage.
    18. The repository risks feature overlap more than missing primitives.
    19. The next work should consolidate before expanding.
    20. Version 1.0 must be evidence-backed rather than mechanism-backed.

    Layered architecture

    1. The production dependency direction is domain to ports to kernel.
    2. Agency depends on kernel-facing contracts and domain values.
    3. Runtime composes agency, kernel and adapters.
    4. Adapters implement ports and do not import agency policy.
    5. Applications select compositions and expose product APIs.
    6. Clients call runtime services rather than owning execution.
    7. Domain has no infrastructure dependency.
    8. Ports do not implement provider-specific behavior.
    9. Kernel remains domain-blind.
    10. Agency remains policy-injectable.
    11. Runtime is the composition and lifecycle authority.
    12. Adapters are replaceable deployment choices.
    13. Packs are declarative policy bundles.
    14. Applications are thin product facades.
    15. This is a hexagonal production lattice.
    16. The lattice prevents provider lock-in.
    17. The lattice also prevents frontend authority leakage.
    18. The lattice makes hermetic testing possible.
    19. The lattice enables local and remote adapters.
    20. The lattice is the primary generalization mechanism.

    4. Evidence models distinguish claims from observations.

    8. Workflow reducers derive workflow state from causal events.
    9. Canonicalisation uses deterministic JSON representations.
    10. Digests bind manifests and artifacts to immutable identities.
    11. Wire contracts define serialized interoperability.
    12. Result types represent success and typed failure.
    13. Selectors rank or filter resources without granting authority.
    14. Domain code should remain deterministic where possible.
    15. Domain code should not inspect environment variables for policy.
    16. Domain code should not call a model.

    18. Domain code should not spawn a subprocess.

    4. Duplicate commands return prior result where safe.
    5. Sequence guards prevent stale client writes.
    6. Event envelopes use canonical serialization.
    7. Content digests prevent silent artifact substitution.
    8. Reducers must tolerate known compatibility versions.
    9. Unknown future events should fail explicitly or be quarantined.
    10. Historical events must not be rewritten.
    11. Projections may be rebuilt from the ledger.
    12. Indexes may be discarded and regenerated.
    13. Telemetry may be incomplete without changing facts.
    14. Missing telemetry is represented explicitly.
    15. A zero value must not masquerade as missingness.
    16. Event writer authority is role-scoped.
    17. Arbitrary plugins cannot emit authoritative events.
    18. Orchestrators emit only their allowed event kinds.
    19. Evaluators cannot rewrite production trajectories.
    20. This yields a single causal truth plane.

    6. User may approve, reject or edit where policy allows.
    7. Decision is validated against the pending challenge.
    8. Approval cannot widen the original grant.
    9. Rejection produces a durable denial event.
    10. Approval produces a durable authorization event.
    11. Runtime resumes from the checkpointed episode.
    12. Prior turns are supplied to the new engine instance.
    13. Prior seen verbs preserve phase and tool policy.
    14. Settled effects are not repeated.
    15. Stale approvals fail closed.
    16. Approval expiry is a typed termination path.

    18. Frontend refresh does not lose a pending challenge.
    19. The same mechanism supports research egress approval.
    20. The same mechanism supports tutor escalation.

    Cancel, timeout and shutdown flow

    3. Active worker receives cancellation intent.
    4. Long-running adapters must observe cancellation boundaries.
    5. Pending effects are reconciled before final state.
    6. Open leases are released or settled.
    7. Cancellation emits a terminal event.
    8. Cancellation must not be confused with provider failure.
    9. Timeout is a typed failure class.
    10. Shutdown persists enough state for restart.
    11. Daemon shutdown should be graceful.
